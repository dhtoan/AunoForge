# AunoForge v0.2 Star-Worthy Growth Design

Date: 2026-09-12
Status: Proposed for implementation after maintainer review

## Goal

Make AunoForge materially easier to try, trust, reuse, and recommend so stars, saves, watches, forks, discussions, and contributions can grow organically from real product value rather than activity gaming.

The v0.2 program should turn the current trustworthy maintainer CLI into a polished GitHub-native experience that a maintainer can understand in under a minute, try without an API key, and adopt without paying a large setup or CI-time penalty.

## Product thesis

AunoForge should earn attention by solving a recognizable maintainer problem better than a generic AI reviewer:

> Run evidence-aware maintenance checks in CI, get a reproducible report, and keep the human maintainer in control.

The strongest differentiators to surface are:

1. **Zero-key first experience** — the mock/deterministic path works without provider credentials.
2. **Evidence-aware findings** — file and line claims are validated against repository evidence.
3. **Human-controlled writes** — read-only by default, no automatic merge, and explicit write boundaries.
4. **Provider neutrality** — Codex/OpenAI and Claude/Anthropic are adapters, not project policy.
5. **Contributor-friendly recipes** — contributors can add useful maintenance knowledge without learning the entire core.

## Anti-gaming constraints

Growth work must preserve the repository's existing OSS credibility rules.

Do not create fake users, fake stars, fake forks, reaction farming, synthetic Q&A, fake co-authors, empty or trivial PRs, meaningless releases, duplicate issues, spam comments, or external-repository PRs/comments without explicit human approval.

Every PR in the v0.2 train must have a real user or maintainer benefit, deterministic acceptance criteria, and test or CI evidence appropriate to its scope.

## Delivery model: controlled PR train

Use one primary upgrade PR at a time.

A new feature PR should start only when the previous primary upgrade PR is merged, closed, or explicitly superseded. Small independent contributor PRs can still be reviewed normally, but maintainer-generated upgrade work should not flood the repository.

For each primary PR:

1. Identify a non-duplicate problem from the roadmap, issue tracker, CI, user feedback, or an observed maintenance gap.
2. Define acceptance criteria before implementation.
3. Add or update tests first when behavior changes.
4. Implement the narrowest complete change.
5. Run lint, typecheck, tests, build, and relevant platform/action smoke checks.
6. Open the PR with evidence and screenshots/output snippets only when they are real.
7. Do not auto-merge.
8. After merge, update the next milestone only if the previous work produced a stable foundation.

## v0.2 milestone sequence

### Milestone 1 — Production-ready GitHub Action packaging

#### Problem

The current composite Action runs `corepack`, installs dependencies with `pnpm install --no-frozen-lockfile`, and builds the monorepo every time a downstream repository invokes AunoForge. This increases startup time, network dependency, supply-chain surface, and reproducibility risk.

#### Design

Keep the public Action interface compatible while replacing runtime installation/build work with a checked-in generated runtime produced by a deterministic build step in the AunoForge repository.

Preferred shape:

- Keep `action.yml` as the public metadata entry point.
- Generate a self-contained Action runtime under a clearly named generated directory such as `dist/action/`.
- Make the consumer Action execute that generated runtime directly instead of installing the monorepo.
- Add a repository build command that regenerates the runtime from source.
- Add CI verification that the committed Action runtime matches source and fails on drift.
- Keep provider credentials optional and preserve mock mode with no external model request.
- Preserve the `report-path` output and existing explicit write boundary.

If bundling the full CLI into one runtime proves brittle, the fallback is a prepacked workspace payload committed for Action use. The consumer must still avoid a fresh dependency install and monorepo TypeScript build.

#### Acceptance criteria

- A downstream workflow can run `uses: dhtoan/AunoForge@<release-tag>` without executing `pnpm install` inside AunoForge.
- The Action performs no source compilation in the consumer repository.
- Mock review works on Linux with no provider key.
- Action runtime generation is reproducible and CI detects stale generated output.
- Existing CLI development flow remains unchanged.
- Least-privilege defaults remain intact.
- Existing tests and action smoke tests pass.

### Milestone 2 — First-class report artifacts and job summary

#### Problem

AunoForge currently writes a report path, but adoption requires users to manually discover and wire the result into their workflow.

#### Design

Make the Action produce a useful GitHub-native result without enabling repository writes.

- Always expose the report path.
- Add a concise GitHub Step Summary containing status, counts, and the report location.
- Add opt-in artifact upload in the composite workflow surface, using GitHub's maintained artifact action and a stable artifact name.
- Keep raw Markdown/JSON report generation available for downstream automation.
- Never post a PR comment merely because an artifact was generated.

#### Acceptance criteria

- Default run produces a readable Step Summary.
- Artifact upload can be enabled independently of PR-comment permissions.
- JSON remains machine-consumable.
- No additional repository write permission is required for summary/artifact mode.

### Milestone 3 — Non-spammy opt-in PR comments

#### Problem

The current comment path creates a new top-level comment every time comment mode runs. Repeated workflow runs can become noisy.

#### Design

Use an AunoForge-owned hidden marker in the comment body and update the existing AunoForge report comment when possible rather than posting a new comment on every run.

Rules:

- Commenting remains disabled by default.
- `comment=true` still requires explicit `allow-write=true` and `pull-requests: write`.
- Only AunoForge's own marked comment may be updated.
- If no marked comment exists, create one.
- If permissions are insufficient, fail clearly without weakening the permission boundary.

#### Acceptance criteria

- Re-running comment mode updates one AunoForge report comment instead of creating duplicates.
- The implementation cannot overwrite arbitrary human comments.
- Fork safety and token handling are covered by tests.

### Milestone 4 — 60-second proof and stable install path

#### Problem

The README explains the architecture well but asks new visitors to absorb a large amount of text before seeing the fastest proof that the project works.

#### Design

Restructure the top of the README around one verified, copy-pasteable success path:

1. What AunoForge protects maintainers from.
2. A 30-60 second zero-key local or CI demo.
3. A real sample output excerpt generated by the current release.
4. Stable GitHub Action usage pinned to a release tag rather than `@main`.
5. Clear links to deeper architecture/security documentation.

Do not use fabricated benchmarks, fabricated adoption numbers, fake testimonials, or unverified comparison claims.

#### Acceptance criteria

- A new visitor can reach a successful zero-key run from the README without reading the full architecture section.
- All commands are tested in CI or a maintained smoke workflow.
- Action examples use the current stable release tag.
- The README still explains security and evidence validation, but below the first-use path.

### Milestone 5 — Marketplace and release readiness

#### Design

Prepare the Action for trustworthy discovery without creating meaningless releases.

- Complete Action metadata and branding fields supported by GitHub.
- Add a maintained example workflow.
- Add release checklist validation for generated Action runtime, docs tag references, changelog/release notes, CI, and smoke tests.
- Publish a new release only when the milestone has user-visible functionality worth releasing.
- If Marketplace submission requires a manual GitHub UI step, document that step and stop before pretending it happened.

#### Acceptance criteria

- Release checklist can be run deterministically.
- Stable Action examples reference a real release tag.
- Release notes are derived from actual merged work.
- No release is created solely to generate activity.

## Star-worthy follow-on features

These are candidates after the v0.2 Action path is stable. They are not pre-approved for implementation merely because they are listed here.

### A. Maintainer health snapshot

Produce a compact, reproducible repository health summary from `aunoforge doctor` that can be attached to CI artifacts or Step Summary. The value is visibility, not a vanity score.

### B. Reproducible issue-to-plan workflow

Make `aunoforge reproduce` generate a contributor-ready reproduction checklist that maintainers can paste into an issue after human review. This should reduce back-and-forth on real bug reports.

### C. Recipe contribution kit

Provide a fixture template, validation command, test command, and one complete example contribution so a new contributor can submit a meaningful recipe without learning internal packages.

### D. Provider compatibility fixtures

Create stable provider-contract fixtures for Codex/OpenAI, Claude/Anthropic, and mock output so adapter regressions are caught before release.

## Organic growth loop

The repository should create reasons for legitimate discovery and return visits:

- High-signal releases with concrete before/after behavior.
- Search-friendly docs around evidence-aware code review, safe AI code review, GitHub Action security, and human-in-the-loop OSS maintenance.
- Real `good first issue` candidates only when work is actually bounded and useful.
- Discussions/Q&A only after Discussions is enabled and there are genuine user questions; never seed synthetic Q&A.
- Contributor recognition based on merged substantive work, never fake co-authorship.
- Public examples drawn from real AunoForge tests/fixtures rather than staged external activity.
- Small demo repositories may be created only if they demonstrate real integration behavior and remain maintained; they must not exist merely to inflate repository count.

## Success signals

Treat these as observation signals, not targets to manipulate:

- Unique external contributors with substantive merged work.
- Stars, watchers, forks, and clones that grow without solicitation spam.
- Repeat Action usage across real repositories.
- Issues that contain reproducible feedback rather than generic praise.
- Discussions with real technical questions.
- External mentions, backlinks, or package/Action usage that can be independently verified.
- Lower Action startup overhead after v0.2 packaging work.
- Fewer duplicate bot comments after sticky-comment work.

## Failure modes to avoid

- Shipping multiple shallow PRs instead of one coherent feature.
- Adding badges without a real program/status behind them.
- Claiming Marketplace availability before it is actually published.
- Publishing releases with only README churn.
- Optimizing README language for hype at the cost of technical clarity.
- Adding autonomous repository writes that contradict the project's human-control thesis.
- Introducing a web dashboard, MCP server, or GitHub App before real usage justifies the maintenance burden.

## Testing strategy

Behavior-changing PRs should use test-driven development where practical.

The v0.2 Action path requires:

- Unit tests for Action input validation and permission boundaries.
- Tests for report file and Step Summary generation.
- Tests for sticky-comment ownership markers before comment updates are enabled.
- Generated-runtime drift verification.
- Linux Action smoke tests using mock mode.
- Existing Node 20/22/24 quality matrix.
- Existing macOS/Windows CLI smoke coverage.
- Fork-safety regression coverage for any workflow receiving pull-request data.

## Initial PR train

1. **PR 1:** production-ready Action packaging and reproducible generated runtime.
2. **PR 2:** GitHub Step Summary + opt-in report artifact.
3. **PR 3:** sticky opt-in PR report comment with ownership marker and safety tests.
4. **PR 4:** README 60-second proof + stable-tag examples, closing the existing stable-tag documentation issue if fully satisfied.
5. **PR 5:** release/Marketplace readiness checks and v0.2 release preparation, only after the preceding PRs are merged and stable.

Each PR is conditional on the preceding work remaining justified after review. If implementation evidence changes the design, update this document or the relevant issue rather than forcing the original sequence.
